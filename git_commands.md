Роль: Разработчик 1. Создание удаленного репозитория GitHub и привязка его к локальному.

Создаем новый репозиторий на GitHub. При необходимости создаем SSH ключи в локальном Bash и экспортируем их на GitHub по инструкции https://github.com/Hexlet/ru-instructions/blob/main/git.md

git remote add origin git@github.com:<username>/<repo name>.git связывает локальный репозиторий с удаленным
   |
   |
git branch -M main переименовывает локальную ветку в main. по умолчанию ветка локального репозитория называется master, что делает невозможным копирование изменений в удаленный реп, т.к. в GitHub локальные ветки по умолчанию называются main
				   Примечание: команда git config --global init.defaultBranch main установит имя будущих локальных репозиториев в main
	|
	|
git push отправляем коммиты в удаленный репозиторий GitHub

Дополнительные команды для работы с локальным репозиторием:

git rm filename удаляет файл и добавляет изменение в индекс (аналог двух команд git rm + git add)

git restore <filename> восстанавливает файл в репозитории (в рабочей среде), при условии если он был удален или изменен. Если изменения добавлены в индекс, восстанновятся изменения из индекса. Если нет, то восстанавливаются изменения из коммита (если он был).
                       Незакоммиченные и не добавленные в индекс изменения будут потеряны безвозратно. Примечание: если для изменений делали коммит, то он останется в репозитории навсегда, даже если пушили изменения на GitHub. 
					   Т.е. файл можно восстановить из коммита в любом случае

git restore --staged <filename> отменяет изменения добавленные в индекс, переводя изменения обратно в рабочую среду. Для файлов у которых уже есть коммит статус вернется на modified, для файлов без коммита статус вернется на untracked

---- Анализ файлов репозитория---------------------------
git diff показывает изменения внесенные в файлы локального репозитория. Только те строки, которые были изменены. Эта команда показывает только изменения, которые еще не добавленные в индекс

git diff --staged тоже самое что и git diff, только показывает изменения уже добавленные в индекс

---- Анализ коммитов репозитория-------------------------
git log показывает список всех коммитов в локальном репозитории отсортированных по дате в обратном порядке

git log -p тоже самое, что и git log, только показывает разницу (git diff) по каждому коммиту в репозитории. Навигация по коммитам может быть объемной, клавиша f - вперед, b - назад, q - выход из навигации

git show <commit ID (hash)> показывает разницу (git diff) по конкретному коммиту. Т.к. хэши имеют большую длину, можно поставить первые 7 символов хэша в качестве ID коммита

git blame <filename> показывает список коммитов по файлу, с информацией кто, когда и в каком коммите его менял

git grep <any text without quotas> ищет указанный текст во всех файлах репозитория. Выводит имя файла и строка, где встречается искомый текст

git grep -i <any text without quotas> тоже самое, что и git grep, только без учета регистра

git clean -fd удаляет файлы/папки которые еще не были добавлены в индекс. По сути это очистка от "мусора", который создали в репозитории и не хотим добавлять в коммит. # -f – force, -d – directory

git revert <commit ID (hash)> отменяет изменения коммита на последние, сделанные до него. Отменить изменения можно в любом коммите репозитория. При этом создается новый коммит с новым ID. 
                              Т.е. git revert не перезатирает коммит в котором необходимо отменить изменения, а создает новый
							  
(!)git reset --hard HEAD~ отменяет последний (головной) коммит. Эту операцию можно делать только в случае, если коммит последний и был создан ошибочно и нет необходимости сохранять о нем историю в репозитории и передавать коммит в GitHub. Ни в коем случае нельзя
					   применять эту команду на коммиты залитые из GitHub (сделанные другими разработчиками) или же если локальный репозиторий уже был залит на GitHub ранее, т.к. это может нарушить целостность репозитория при общей работе с ним 
					   нескольких разработчиков. После тильды можно указать количество коммитов, которые необходимо удалить. Например: git reset --hard HEAD~3
		     
			 --hard <commit ID (hash)> с этим параметром, команда откатывает всю историю коммитов репозитория до указанного commit ID в параметре. При это удаляется вся история коммитов, удаляются все изменения добавленные в индекс и
		               все файлы в рабочей директории. Использовать команду вообще нежелательно. Откатить обратно изменения можно командой git reset --hard HEAD@{1}, но она действует в короткий промежуток времени после отмены коммитов,
					   пока сборщик мусора окончательно не удалил изменения.
					   
			 --soft отменяет коммит, но сохраняет его изменения в индексе. Таким образом изменения становятся снова готовыми к коммиту
			 
			 --mixed отменяет коммит и изменения добавленные в индекс, но оставляет изменения (файлы) в рабочей директории. По умолчанию, команда git reset без параметров работает в режиме --mixed
			 
git commit --amend изменяет последний сделанный коммит. Под капотом команды выполняется команда git reset по отношению к последнему коммиту, ID начального коммита и измененного разные. Этой командой можно добавлять файлы в коммит по необходимости.
           --no-edit необязательная опция, при указании которой не будет вызван редактор описания коммита. Описание останется как у изначального коммита.
		   
git commit <filename> добавляет в индекс изменения и одновременно делает коммит по указанному файлу

git commit -a добавляет в индекс все изменения рабочей директории (аналог git add .) и делает одновременный коммит. Примечание: при множественных изменениях затруднительно потом изучать историю такого коммита
							 
git add -i (--interactive) включает интерактивный режим добавления изменений в индекс. С помощью этого режима можно добавлять в отдельные изменения файла (например: разные строки добавленные разными разработчиками) в индекс, вместо добавления в индекс 
                           всех изменений разом. Такие мелкие изменения называются hunk. Они полезны, когда в один файл с кодом были внесены разные изменения, например, новая функция + рефакторинг кода + вызовы функций внешних пакетов, а необходимо закоммитить
						   только отдельный функционал, напрмер только рефакторинг. Использование git add в данном случае неоправдано, т.к. в индекс будут добавлены все изменения по файлу. Интерактивный режим предлагает выполнение нескольких подкоманд:
						   1:status показывает список файлов со статусами
						   2:update добавляет в индекс файлы целиком (аналог git add)
						   3:revert отменяет последние изменения добавленные в индекс и возвращает их в рабочий каталог со статусом modified
						   4:add untracked добавляет в индекс новые файлы, ранее неотслеживаемые
						   5:patch добавление hunk'ов в индекс. patch режим предлагает подкоманды работы с hunk'ами
						           y — yes: добавить этот ханок в индекс.
								   n — no: пропустить этот ханок.
								   q — quit: выйти из режима патчинга (сохраняя то, что уже успели зашейдить в этой сессии).
								   a — all: добавить этот и все оставшиеся ханки текущего файла.
								   d — do not stage this or any of the remaining hunks in this file (пропустить весь файл).
								   e — edit: открыть ханок в текстовом редакторе. Можно вручную удалить строки с плюсом (+), которые вы не хотите коммитить прямо сейчас, сохранить файл и вернуться в интерфейс.
								   s — split: разбить большой ханок на более мелкие части (работает не всегда, если изменения стоят слишком плотно друг к другу).
								   ? — помощь.
						   6:diff показывает разницу между рабочей директорией и текущим состоянием индекса
						   7:quit выход из интерактивного режима
						   ?:help справка
